## 场景：follow-builders prepare-digest.js 远程 fetch 间歇性失败（000 / "fetch failed"）

**日期**：2026-07-12
**来源任务**：Automation — AI Builders Digest 日报
**标签**：`follow-builders` `fetch-flaky` `retry` `robust-fetch` `network`

### ⚠️ 踩坑

- `prepare-digest.js` 对 3 个 feed + 5 个 prompt 用 `Promise.all([fetchJSON(...), ...])` 一次性拉取，**零重试**。
- 当任一远程 URL（实测 `feed-blogs.json`、`prompts/translate.md`）出现连接级 `fetch failed`（curl 探测返回 `000`，非 404）时，整次 `main()` 被 reject，stderr 仅 `{"status":"error","message":"fetch failed"}`，stdout 为空 → 获取连败 2 次。
- 同会话内 `curl github.com`=200、`node fetch google`=200，说明**不是整体断网**，而是 raw.githubusercontent.com 部分资源间歇性握手失败（DNS/TLS/限流随机掉线）。

### ✅ 打法（已验证）

- 自写健壮抓取脚本（参考 `/tmp/fb-prepare-robust.mjs`），核心：**每个 URL 单独重试**（6 次、指数退避 + 抖动），不共用一个 Promise.all。
- feed 兜底顺序：远程(重试) → 技能目录内置 `feed-*.json`（仅当远程彻底不可达，且**必须打 STALE 标记告知用户，绝不冒充"今日"内容**）→ 否则报错。
- prompt 兜底顺序：用户自定义 > 远程(重试) > 技能内置。
- 输出 schema 与官方 `prepare-digest.js` 完全一致，下游 HTML 生成脚本无需改动。
- **铁律**：技能内置 `feed-*.json` 是 4/27 旧快照，绝不能作为"当天 digest"内容来源；远程失败只能重试，不能拿旧数据顶替。
- 验证：重试脚本一次跑通，103KB 合法 JSON，`feedGeneratedAt` 为当日（2026-07-12T01:19Z）。

## 场景：feed 里的 blog 长期滞留旧条目 → 需按"是否已收录"去重，而非照抄 stats

**日期**：2026-08-02
**来源任务**：Automation — AI Builders Digest 日报
**标签**：`follow-builders` `blog-dedup` `stats口径` `数据质量`

### ⚠️ 踩坑

- `stats.blogPosts` 只统计 feed 里 blog 数组的长度，**不判断新鲜度**。
- 实测 2026-08-02 的 blog 唯一条目是 `Claude Code now supports artifacts`（publishedAt = **Jun 18, 2026**），该条目在 **7/8 的 digest 已收录过**；feed 侧的 blog 源刷新频率远低于 X/Podcast，会长期滞留同一篇。
- 若直接把 `stats.blogPosts=1` 写进 stats strip 和 index meta，会让读者以为当天有新博客，实际是一个半月前的旧文。

### ✅ 打法

1. **blog 必须按 `publishedAt` + 历史收录记录二次判定**，不能直接用 `stats.blogPosts`：
   - `publishedAt` 距当日超过 ~7 天 → 高度可疑
   - 去 automation memory.md 里 grep 该标题是否已出现过 → 命中则判为旧条目
2. 判为旧条目时：**正文不渲染该 blog 卡片，stats 与 index meta 的 Blog 一律计 0**，并在 automation memory 里写明判定理由（哪天已收录）。
3. 同样的判定逻辑适用于 Podcast——但实测 Podcast 刷新正常，主要风险在 blog。
4. **stats 口径铁律**：HTML stats strip 的四个数字必须与 index.html 的 `meta` 字符串完全一致，且都以"实际渲染进正文的内容"为准，不以 JSON 的 `stats` 原值为准。

### 🔁 2026-08-03 复现验证：同一 blog 已滞留 3 个月，去重规则必须查全量历史

- 8/3 feed 的唯一 blog 仍是 `How we contain Claude across products`，且**连 `publishedAt` 字段都是 `None`**——比 8/2 那次更难判新鲜度。
- 仅 grep automation memory.md 只命中 1 处（6/30），**容易误判为「只收录过一次、可以再发」**。
- **升级后的判定命令**（必须同时查两处）：
  ```bash
  # ① 查 automation 记忆
  grep -c "<blog 标题>" .workbuddy/automations/<id>/memory.md
  # ② 查已发布 HTML 全量（更权威）
  grep -rl "<blog url slug>" 2026/
  ```
  实测 ② 命中 `2026/06/05`、`2026/06/21`、`2026/06/30` 三份 —— 该 blog 已滞留近两个月。
- **铁律补充**：`publishedAt` 为 `None` 时不能默认「新条目」，必须走 ② 的全量 HTML grep；命中即计 0。

---

### 📌 X/Twitter 卡片数与 tweet 数的口径

- 本期 13 位 builder 中，有几位只挑选了部分推文（如 Sam Altman 3 条只取 1 条、Nikunj 3 条只取 1 条——其余是纯链接/生活向内容无实质观点）。
- 因此 **Tweets 计数必须按"实际渲染的 URL 条数"统计（21），不能用 `stats.totalTweets`（31）**。生成脚本里用 `sum(len(tweets) if idxs is None else len(idxs))` 动态算，避免两处对不上。

## 场景：GitHub Pages 部署后 URL 短暂 404（Actions 构建延迟）

**日期**：2026-08-04
**来源任务**：Automation — AI Builders Digest 日报
**标签**：`github-pages` `deploy-wait` `verification` `gh-run`

### ⚠️ 踩坑

- `git push` 成功后立刻 `curl` 验证页面，返回 **HTTP 404**（返回约 9KB 的 GitHub 404 页，非 digest）。
- 原因：仓库用 `.github/workflows/deploy.yml`（actions/deploy-pages）在 push 到 main 时整库构建部署，run 约需 19–22s 才 `completed`。

### ✅ 打法

- push 后**不要立即 curl 判失败**；先 `gh run list --limit 1` 确认状态变 `completed/success`（通常 <30s），再 curl 验证 HTTP 200。
- 修正计数后二次 push 同理：第二次 push 的 run 仍 `in_progress` 时线上还是上一次产物，等 completed 再验。
- 验证命令：`code=$(curl -s -o /tmp/p.html -w "%{http_code}" <url>)`；digest 页 stat-num 与 label 分行，grep 用 `<div class="stat-num">21</div>` 而非连续串 "21 Tweets"。
- `gh` CLI 在本机可用且已认证，可直接 `gh run list` 监控部署，比盲等 curl 更稳。

## 场景：stats 口径两条规则冲突时的最终裁决（2026-09-08）

**日期**：2026-09-08
**来源任务**：Automation — AI Builders Digest 日报
**标签**：`stats口径` `规则冲突` `rendered-vs-feed` `数据质量`

### ⚠️ 冲突

项目经验库里存在两条互不一致的 stats 规则：
- 2026-08-02 铁律：stats strip 与 index meta **必须一致，且以"实际渲染进正文的内容"为准**，不以 JSON `stats` 原值为准（该条针对 blog 长期滞留旧条目）。
- 09-03 ~ 09-07 连续实践：stats 报 **feed 总数**，同时按 skill 的 summarize_tweets 规则跳过一部分薄内容推文（如纯梗图 / 政治 / engagement fluff）→ 结果 stats 数字 > 正文实际渲染数，日历上出现系统性虚高。

### ✅ 裁决（本期起执行）

**让"渲染数"去追平"feed 总数"，而不是反过来把 stats 改小。**

具体做法：对 feed 里的每一条内容都渲染，薄内容（调侃、一句话反应、纯链接）不删除，而是**各配一句克制的定性说明**（如"论证层面很薄，但如实反映了……的随意程度"），让读者自行判断价值。这样：
- 渲染数 == feed 总数 == stats strip == index meta，四处数字必然一致，无需人工对账；
- 不违反 skill 的"绝不编造"规则（没有替薄内容虚构观点）；
- 也不违反 08-02 铁律（统计的就是渲染出来的东西）。

**判断顺序**：① feed 内容是否陈旧/已收录（走既有去重规则）→ 剔除后得到 feed 有效总数；② 有效总数内全部渲染；③ stats/index meta 填该总数。
**只有一种情况可以把 stats 改小**：某条内容被去重规则判为"旧条目/已收录"而剔除（如 08-02、08-03 的 blog）。编辑性地跳过薄内容**不属于**这种情况。

**根因提示**：把"编辑判断（要不要写深写浅）"和"统计口径（算不算一条）"混为一谈，是这类不一致的根源。前者影响措辞，后者影响数字，两者必须解耦。

## 场景：跳过一天后不要补发，feed 快照本就滞后约 1 天（2026-09-10）

**日期**：2026-09-10
**来源任务**：Automation — AI Builders Digest 日报
**标签**：`feed-lag` `missed-day` `no-backfill` `calendar-integrity`

### ⚠️ 观察

- 2026-09-09 未生成（日历上 `2026/09/09/` 目录不存在），09-10 触发时拿到的 feed 是 **2026-09-09T06:41Z** 的快照。
- 历史对照：09-08 那期用的 feed 是 2026-09-07T06:50Z —— 说明 feed 生成时刻比 digest 日**滞后约 1 天是常态**，不是"陈旧告警"。

### ✅ 打法

1. 跳过 1 天后，**次日那期直接把该快照当当天内容发布**，不回头补发前一天的条目。
   - 理由：补发会用到同一份 feed，等于同一批内容在日历上出现两次，污染 streak 与"每日覆盖"的可信度。
2. 只在 automation memory 与当日日志里**如实标注空档 + 该期 feed 的 `feedGeneratedAt`**，供日后判重时参考。
3. 与 07-03 的"stale snapshot"规则区分开：
   - **连续两日 `feedGeneratedAt` 完全相同** → 判为 feed 冻结（07-03 规则）
   - **滞后 1 天但快照前进了一天** → 正常，照发（本条）
4. 判重时（blog / podcast）用内容级 grep 而非日期，见 09-08 条目。

### 🔁 2026-09-13 复现：跳过一天会**永久丢掉一份快照**

- 09-12 未运行，09-13 触发时 feed 是 `2026-09-12T06:36Z`，比 09-11 那期用的 `2026-09-10T06:40Z` 前进了 **2 天**。
- 与 09-10 那次（跳 1 天、快照只前进 1 天、内容没丢）**不同**：本次 `2026-09-11T06:xx` 那份快照随着 09-12 被跳过而**永久无法追回**——feed 只保留最新一份。
- **处置不变**：不补发被跳过的那天，把最新快照作为当天一期发布；但在 automation memory 与当日日志里注明「丢档：XX 日快照未采集」，供日后判断 streak 缺口时参考。
- **推论**：这个 feed 没有历史回放接口，任何一次未触发都会造成内容缺口，无法通过次日补跑找回。

- 按既有经验"先 `gh run list` 轮询到 completed/success 再 curl"，本期写成：
  `gh run list --workflow "pages-build-deployment" --limit 1 --json status,conclusion`
- 该 workflow 名在本仓库**不存在** → 返回空数组 → `-q '.[0].status'` 输出空串 → `case` 三个分支都不匹配 → `sleep 10` 后重试，**跑满 20 次 / 25 分钟**，后台任务被系统自动挂起才停下。

### ✅ 正确做法

1. **不要指定 `--workflow`**，直接看最近一条：
   ```bash
   gh run list --limit 1 --json displayTitle,status,conclusion,databaseId
   ```
2. **本仓库的部署 workflow `displayTitle` = commit message**（如 "AI Builders Digest 2026-09-11"），不是 GitHub 默认的 `pages-build-deployment`。仓库里是自定义 Actions workflow，不是 GitHub 原生的 Pages 构建。
3. **轮询必须带兜底退出**：`for i in $(seq 1 N)` + 空值也计入尝试次数，宁可超时也不要静默空转。更好的写法是用 `gh run watch <id>`，自带超时。
4. 顺序不变：Actions `completed/success` → 再 `curl -I` 判 200。本期确认该顺序有效，子路径**首查即 200**（未遇 CDN 边缘 404）。

### 一句话记住

**轮询前先确认查询能返回东西。** 空结果不是"还没开始"，是"查错了"。

## 2026-09-17 · 推文 URL 计数校验的 grep 贪婪陷阱
**场景**：生成后按既定校验清单跑「唯一推文 URL 数 == stats 的 Tweets」。
**踩坑**：沿用旧命令 `grep -o 'https://x.com/.*/status/[0-9]*' file | sort -u | wc -l`，结果输出 **14**（= 卡片数）而不是 27（= 推文数），一度以为渲染漏了一半。
**根因**：`.urls` 里所有 `<a>` 都在**同一行**，贪婪 `.*` 会从该行第一个 `https://x.com/` 一路吞到最后一个 `/status/<id>`，整行只产出 **1 个匹配**。所以计数实际等于"有多少个 `.urls` 行"，与推文数无关——当每个 builder 只有 1 条推文时数字会碰巧对上（所以之前几期没暴露）。
**正确写法**：用字符类限定路径段，禁止跨段贪婪：
```bash
grep -o 'https://x\.com/[a-zA-Z0-9_]*/status/[0-9]\+' file | sort -u | wc -l
```
**更强的校验**：把抽出的 ID 与 feed 原始 ID 列表 `diff`（`grep -o ... | sed 's#.*/status/##' | sort -u` vs feed 的 `t.url` 抽取结果），两者完全一致才是真的没问题。
**来源任务**：automation-1777275206372 / 2026-09-17 AI Builders Digest
**标签**：#digest #校验 #grep #shell
